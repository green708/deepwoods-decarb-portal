1 Overall Assessment

High-level quality summary for the platform as a whole.
Verdict: Premium sustainability SaaS with a genuinely solid foundation. The design token system, component architecture, and core layout patterns are all production-quality. The score is held back by a cluster of P0 visual inconsistencies — most of which are a few lines of CSS away from being fixed — and a lack of shared components for modals, empty states, and form inputs.

Key blocking issues: Sidebar has zero visual separation from page content (same background color). Nav active state uses hardcoded red (#FF2800) — breaks multi-tenancy and looks wrong on a sustainability product. Background token is too heavy. These three fixes alone would move the score to ~82.

2 Design Strengths

Current design decisions that are working well and should be preserved.
  • PageHeader / PageBody / StatCard / Section component system (portal.tsx) — Consistent structural components used across the interior. StatCard shadow system is polished; Section headings with dividers give pages clear hierarchy.
  • Layered box-shadow card system — Cards use a soft multi-layer shadow that gives depth without being heavy. Consistent across all StatCards and chart containers.
  • CSS design token system (src/styles.css) — Semantic color tokens (--primary, --sidebar, --background, --destructive), radius tokens, and shadow utilities are well-structured. The architecture is right; some tokens just aren't being used yet.
  • Login / Request Access two-panel layout — Dark-left / light-right split with the platform tagline on the left is a premium SaaS pattern. Well-executed with good whitespace.
  • Scope 1 / 2 / 3 color coding — Consistent teal / navy / slate color assignment across all Recharts charts. Users can quickly orient themselves across multiple chart types.
  • Entity / FY switcher bar pattern — The sticky entity + fiscal year switcher at the top of each interior page is excellent contextual UX. Users always know which entity and year they're viewing.
  • PendingActivation holding screen — Clean, purposeful design for users awaiting activation. Communicates status clearly without exposing internal process detail.
  • Custom scrollbar styling — Thin, rounded scrollbar with brand-consistent color. Small detail that reinforces the premium feel.
  • Mobile slide-in nav — Overlay navigation with backdrop works correctly on small viewports. Doesn't break the layout.
  • GroupNav accordion pattern in sidebar — Collapsible navigation groups (Carbon Footprint, Decarbonisation, Compliance) keep the nav scannable without exposing all routes at once.

3 Critical UX Problems

Issues categorised by severity. P0 = blocking quality bar; P1 = major UX gap; P2 = polish.

P0 — Critical (must fix before any client demo)

P0 Sidebar has zero visual separation from page content _app.tsx / styles.css
Sidebar uses var(--background) which resolves to #E5E5E5 — the same color as the main page background. There is literally no visual boundary between the navigation and the content area. The --sidebar: #FFFFFF token is correctly defined in styles.css but never applied to the sidebar element.
Fix Apply background: var(--sidebar) to the sidebar container in _app.tsx. Add a border-right: 1px solid var(--border) for additional separation.
P0 Nav active state hardcodes #FF2800 red _app.tsx
The active nav item background and indicator are hardcoded to #FF2800 — an aggressive traffic-light red. This directly violates multi-tenancy (every client should see their own primary color) and is visually jarring on a sustainability platform. For a platform whose visual identity is green, this red active state is actively misleading.
Fix Replace all #FF2800 occurrences with var(--primary). Add a CSS variable --nav-active-bg in styles.css set to color-mix(in srgb, var(--primary) 12%, transparent) for the background tint.
P0 --background token is too visually heavy styles.css
--background: #E5E5E5 is a medium gray — noticeably darker than industry-standard SaaS page backgrounds. Combined with the sidebar being the same color, the entire app looks flat and compressed. Premium products typically use #F8FAFC or #F3F4F6.
Fix Change --background to #F3F4F6 (or #F8FAFC for even lighter). Also remove the hardcoded bg-[#F2F2F2] Tailwind class on the main content wrapper and replace with bg-background.
P0 Emoji icons in onboarding role selection onboard.tsx (Slide 3)
Slide 3 of the onboarding tour uses emoji (👑📊📝👁️) as role icons. This reads as a draft or prototype artifact, not a production SaaS product. Emoji render inconsistently across operating systems and are not accessible to screen readers with meaningful labels.
Fix Replace with Lucide React icons: Crown (Admin), BarChart2 (Sustainability Team), Upload (Uploader), Eye (Leadership). Render inside a small rounded icon container with brand-color background.
P0 Nav section label uses inline client.primary_color _app.tsx
The "Decarbonisation Journey" sidebar section label applies client.primary_color as an inline style. For the current client (Featherlite, primary = red), this label appears in red inside the sidebar — looks like an error indicator, not a navigation group label.
Fix Remove the inline color override. Section labels should use the standard muted text style (text-muted-foreground) or a fixed-opacity version of the primary color that doesn't risk looking like an alert.
P0 Loading state is a bare spinner with no context _app.tsx
The app loading state renders a raw <Loader2> spinner centered on screen with no branding, no message, and no error handling visual. Config errors surface raw technical text directly to users.
Fix Create a branded loading screen: platform logo, "Loading your workspace…" message, and a subtle spinner. For config errors, show a friendly "Something went wrong — please refresh or contact support" message instead of the raw error string.
P0 Main content area uses hardcoded bg-[#F2F2F2] _app.tsx
The main content wrapper has bg-[#F2F2F2] as a hardcoded Tailwind arbitrary value. This bypasses the CSS token system entirely, making it impossible to theme or adjust the background via CSS variables.
Fix Replace bg-[#F2F2F2] with bg-background (the Tailwind class that maps to var(--background)).

P1 — Major (fix before next client onboarding)

P1 No shared EmptyState component — each page handles (or ignores) it differently portal.tsx + multiple pages
Many pages show nothing, a loading spinner, or minimal text when data is absent. There is no consistent EmptyState component with an icon, heading, description, and optional CTA. The inconsistency is most visible on Vault, Inventory, and Submissions pages.
Fix Add an EmptyState component to portal.tsx with props: icon, title, description, action?. Adopt it across all data-driven pages.
P1 Two competing style systems: inline style objects vs Tailwind login.tsx, request-access.tsx vs all interior pages
Public pages (login, request access) use inline style={{}} JavaScript objects for all styling. Interior pages use Tailwind utility classes. While the visual output of the public pages is good, this creates two maintenance paths and makes global design changes harder.
Fix Migrate public page inline styles to Tailwind classes in a follow-up refactor sprint. Not urgent visually, but important for long-term maintainability.
P1 Raw technical error messages exposed to users ClientContextGate, multiple pages
Error states in ClientContextGate and several pages display raw JavaScript error strings. Users should never see stack traces, API endpoint URLs, or internal error codes.
Fix Create a standardized error display: friendly message, retry button, and a reference code (for support). Log the raw error to console only.
P1 EntityBar label text is 9px — below accessible minimum entity.tsx
The entity and fiscal year labels in the switcher bar use font-size: 9px. WCAG 2.1 recommends a minimum of 12px for non-decorative text. At 9px, these labels are illegible on standard-DPI displays for older users.
Fix Increase to minimum 11px (preferably 12px). Use font-size: 0.6875rem for maintainability.
P1 LockedState component has no CTA slot portal.tsx
The LockedState component shows a lock icon and message but offers no actionable next step. Users in a locked state need direction — typically "Contact your administrator" or a specific upgrade prompt.
Fix Add an optional action?: ReactNode prop to LockedState. Callers can pass a button or contact link as appropriate.
P1 Onboard Slide 3 role cards have decorative-only borders onboard.tsx
The role selection cards on Slide 3 have very thin, light borders that make them look like informational tiles rather than interactive selection elements. No selected-state visual feedback is visible before selection occurs.
Fix Increase border to 2px. Add a hover state with border-color transitioning to var(--primary). Show a checkmark icon on selection.
P1 Admin client row button groups overflow on narrow viewports admin.tsx
Each client row in the admin panel has a row of action buttons (Activate, Edit, Invoice, etc.). On viewports narrower than ~1100px, these buttons overflow or stack in visually broken ways.
Fix Consolidate secondary actions into a kebab menu (MoreHorizontal icon + dropdown). Keep only the primary action as a visible button.

P2 — Polish (next design sprint)

P2 Chart color palettes defined as in-file constants dashboard.tsx, hotspots.tsx, others
Chart colors are defined as hardcoded hex arrays inside component files. They cannot be overridden by the CSS variable system or swapped for client theming.
Fix Define chart palettes as CSS variables in styles.css (--chart-1 through --chart-6). Reference via getComputedStyle or CSS custom properties in SVG fills.
P2 font-serif maps to Inter (same as sans-serif) styles.css
The font-serif Tailwind class is configured to resolve to the Inter stack, identical to font-sans. This creates a misleading semantic that will confuse future developers.
Fix Either remove the font-serif override or point it to a distinct typeface if serif typography is intentional for some contexts (e.g. report headings).
P2 Reporting simulator looks like a developer tool reporting.tsx
The reporting cycle simulator page uses technical labels, raw dropdowns, and a layout that reads as an internal admin debug view. If client-facing, it needs a UX pass to feel like a product feature.
Fix Add page context description, humanise control labels, and use consistent card layout. If it's admin-only, move it behind the deepwoods_admin role gate and mark it clearly as internal.
P2 Mobile nav slide animation could be smoother _app.tsx
The mobile nav overlay uses a CSS class toggle for show/hide. The slide-in animation is functional but lacks an easing curve and the backdrop fade-in is slightly jarring.
Fix Use transition: transform 200ms cubic-bezier(0.4, 0, 0.2, 1) on the sidebar panel. Fade the backdrop separately with transition: opacity 150ms ease.
P2 DeecarbAI floating button z-index management DeecarbAI.tsx
The AI assistant floating button can be obscured by modal overlays and in some scroll positions sits on top of footer content. Z-index layering needs a global review.
Fix Define a z-index scale in styles.css (--z-modal: 50; --z-overlay: 40; --z-sticky: 30; --z-fab: 25). Apply consistently. Ensure FAB is below modal z-index.
P2 tabular-nums utility not consistently applied to KPI numbers portal.tsx, dashboard.tsx, others
The num utility class (which applies font-variant-numeric: tabular-nums) is defined but not consistently applied to all dashboard numbers and KPI values. Proportional digits cause jitter when values update.
Fix Apply className="num" (or tabular-nums) to all StatCard values, chart axis labels, and animated counters.

10 Accessibility Findings

WCAG 2.1 AA compliance evaluation across key interaction patterns.
Category Finding Status WCAG
Focus States :focus-visible ring defined globally in styles.css. Applied consistently across interactive elements. PASS 2.4.7
Color Contrast — Body Text Navy text (#1F2937) on white background: ~14:1 contrast. Well above AA minimum. PASS 1.4.3
Color Contrast — Muted Text Muted text (#6B7280) on white: ~4.6:1. Passes AA for normal text (≥4.5:1) but borderline at small sizes (<14px). The 9px EntityBar labels are likely failing. BORDERLINE 1.4.3
Icon-Only Buttons Several buttons use icons without visible text labels or aria-label attributes. Screen readers cannot identify these controls. FAIL 4.1.2
Form Label Association Most forms have visible label text. However, for/id linkage between labels and inputs is not always present — particularly in dynamically rendered form fields. PARTIAL 1.3.1
Modal ARIA Roles Custom modal divs lack role="dialog" and aria-modal="true". Screen readers cannot distinguish modal content from page content. No focus-trap is implemented. FAIL 4.1.2
Keyboard Navigation — Nav GroupNav accordion items are focusable and keyboard-operable via standard tab order. No custom keyboard handler required. PASS 2.1.1
Skip Links No "Skip to main content" link present. On keyboard navigation, users must tab through the entire sidebar before reaching page content. MISSING 2.4.1
Page Titles Each route should have a unique <title> element. TanStack Router supports head() per route — audit whether all routes set meaningful titles. UNVERIFIED 2.4.2
Color as Sole Indicator Scope 1/2/3 chart colors use color as the primary differentiator. Chart legends use color blocks + text labels, which is adequate. Confirm that color-blind-safe palette is used (avoid red/green pairing for Scope data). REVIEW 1.4.1
Text Size (EntityBar) 9px label text in the entity bar is below the practical minimum. Older users and users with low vision will struggle to read it. FAIL 1.4.4

14 Remaining Design Debt

Known design issues not addressed this session. Prioritised for future sprints.
▲
Shared Input / Select / Textarea component library
No shared form field components exist. Every form reimplements focus states, border-radius, padding, and error display independently. Building a shared set (Field, Input, Select, Textarea, FieldError) would eliminate most form inconsistency at once. High effort, high value.
●
Chart color palette — CSS variable migration
All chart color arrays are currently in-file constants. Migrating to CSS custom properties (--chart-1 through --chart-6) would enable client-level theming of chart colors and dark mode support. Medium effort.
●
Reporting simulator UX review
The reporting cycle simulator currently looks and feels like a developer debug tool. It needs a product decision (client-facing vs. admin-only) followed by a UX pass to humanise labels, add a page context description, and use consistent card layout.
●
Admin Kanban pipeline tab
The Kanban pipeline tab in admin.tsx requires visual validation. It is unclear whether the current implementation is production-ready or a work-in-progress. Needs a product review before a design pass.
●
Methodology page — dynamic content migration
The methodology page contains hardcoded Featherlite-specific content (base years, scope coverage, emission factor sources). This content should be driven by client configuration data in the database, not embedded as static strings in the component.
●
Mobile overflow audit for wide data tables
Data-dense tables (Green Finance, Admin client list, Inventory) have not been fully audited for mobile overflow behavior. Tables should scroll horizontally within a contained wrapper rather than breaking the page layout.
ⓘ
Accessibility — ARIA attributes on modals and icon buttons
Custom modal overlays need role="dialog", aria-modal="true", and a focus-trap implementation. Icon-only buttons across the app need aria-label attributes. A "Skip to main content" link should be added as the first focusable DOM element. These are WCAG 2.1 AA failures.
●
Public page style migration (login / request-access)
login.tsx and request-access.tsx use inline JavaScript style objects. The visual output is correct, so this is low-priority, but migrating to Tailwind utility classes would make global design changes (font size, border-radius, color) easier to apply consistently.
●
Contextual help system
No tooltip system or inline help icons exist. MSME users encountering terms like "tCO2e", "fugitive emissions", or "CEA emission factor" have no in-context way to understand them. A lightweight tooltip-based help system or a "?" icon linking to the methodology page section would significantly improve usability.
●
Shared Dialog component
Five different modal implementations exist across the codebase. Consolidating to a single shared Dialog component (or adopting shadcn's Dialog primitive) would give consistent keyboard behavior, focus management, scroll-lock, and backdrop handling across all modals.
Estimated effort to close all remaining debt: ~3–4 development sprints. The shared form component library is the highest-effort item (1–2 sprints alone). Accessibility fixes, chart migration, and the contextual help system can each be done in a focused half-sprint.
